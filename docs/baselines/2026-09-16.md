# Baseline 2026-09-16 — what it shows

The capture is `2026-09-16.json`, taken by Catapult's `stats-baseline` workflow
([run](https://github.com/SwaggerAllen/catapult/actions/runs/35150647404)) at
`2026-09-16T21:08:14Z`. This note is the reading; the file is the evidence, and a later
comparison re-runs its queries rather than these sentences.

## Ticket time is overwhelmingly the author's

Total time across the twelve non-terminal, non-queue states, `on=completed`, all
milestones: **1047.2 h**.

| | hours | share |
| --- | ---: | ---: |
| Waiting on the author — `design_review`, `triage`, `blocked` | 850.6 | **81.2%** |
| Agents and CI — `designing`, `in_progress`, `reconciling`, `checks` | 100.9 | 9.6% |
| Queues and `merged` | 95.7 | 9.1% |

The three author states are author-held by DESIGN §3's own table, not by a classification
invented here: `Design review` is "**Author.** Artifacts ready, not yet approved",
`Blocked` is "Author, now", and Triage is where findings go "so the author can accept or
decline them in one keystroke".

`design_review` alone is **523.7 h over 83 tickets — 6.31 h a ticket.**

## The `agentTotal` decision was worth more than it looked

`PLAN.md` C0 says to baseline the per-state rows and never the `agentTotal` rollup, on the
argument that it sums three actors this cutover moves independently. Measured, the
argument is stronger than it was stated:

```
agentTotal                 624.7 h
  of which design_review   523.7 h   = 83.8%
```

**A baseline on `agentTotal` would have been 84% author latency wearing the word "agent".**
Every later comparison against it would have read a change in the author's response time as
a change in the pipeline's speed.

This is also the measurement behind the defect the README records: `design_review` is in
`AGENT_STATES` in `worker/projectstats.ts`, and it fails that list's own test — the comment
excludes states "where nothing is running and no minute is being spent".

## The minutes half is a window, not a total

The two halves have different completeness, and the watermark is why the README puts it
first:

| half | source | coverage |
| --- | --- | --- |
| time in state | recomputed from the tracker every pass | complete |
| Actions minutes | insert-only run table, watermarked | **from 2026-08-26 02:52 only** |

The first milestone opens **2026-08-12 18:53**, so the run table misses roughly the first
two weeks of the project. SETUP §9 gives both reasons — GitHub's run data ages out, and the
backfill "grinds down a night at a time" — and neither is recoverable now.

**So a later comparison must slice both captures to a common `from=`, not compare
all-time totals.** Comparing this capture's "all" bucket against a future one would report
a rise that is entirely the collector having seen more.

The monthly buckets are in the file and are the safer comparison. As taken (September is
partial, to the 16th):

| month | agents + CI | author |
| --- | ---: | ---: |
| 2026-08 | 68.9 h | 642.1 h |
| 2026-09 | 32.1 h | 208.5 h |

## What this means for §9's check

Recorded here and applied in `ops-free-pipeline.md` §9: **"does a ticket reach `Done`
faster" is the wrong headline**, because 81.2% of the answer is author latency and nothing
in C0–C6 touches it. The cutover is judged on the states it moves, and author latency is
tracked beside that rather than mixed into it.
